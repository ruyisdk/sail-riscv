# Ztt test generation

This directory generates bare-metal, self-checking Ztt assembly tests from the manual instruction
snapshot and from test inputs defined in code. The goal is to keep the instruction catalog in sync
with the manual, and to provide repeatable encoding and execution smoke tests for the implemented
model. The test inputs are defined in code and can be read directly from the instruction
definitions and the generated assembly.

## Run matrix

`run_ztt_tests.py` handles the generation, compilation and execution of the full N/UDS/M/ACC
configuration matrix (120 configurations); CMake only regenerates the Sail model and the GAS
macros from the manual snapshot and validates that the two are in sync. The script is resumable:
already generated source files, already compiled ELFs and already recorded results are reused, so
an interrupted run continues from where it stopped.

```sh
# Run the full matrix against an already built simulator
python3 test/ztt/run_ztt_tests.py \
    --sim build/c_emulator/sail_riscv_sim \
    --work-dir build/ztt-matrix

# A single configuration: only regenerate and run it
python3 test/ztt/run_ztt_tests.py --combo n8_u8_m32_a4 \
    --sim build/c_emulator/sail_riscv_sim

# Narrow the scan range on either axis with a comma-separated list. Legal values follow the
# manual: N is a power of two (AME_NELEM is a power of four, the manual sets no upper bound --
# N = 128, i.e. the rv64-ztt-16k-8 configuration), UDS is a power of two, M is 16 or 32, and
# ACC is 1/2/4/8/16.
python3 test/ztt/run_ztt_tests.py --n 8,32 --uds 16 --acc 4

# Generate + compile only (no simulator needed)
python3 test/ztt/run_ztt_tests.py

# List the 120 configurations
python3 test/ztt/run_ztt_tests.py --list
```

The runtime configuration of each configuration is rendered from `cfg/rv64d_v256_e64_ztt.json.in`
after rewriting the Ztt parameters, so the matrix does not depend on the JSON files generated by
CMake. `--jobs` controls parallelism and `--timeout` controls the simulator timeout of a single
test. Pointing `--sim` at spike reuses the same pipeline.

A configuration name has the form `n<N>_u<UDS>_m<M>_a<ACC>` (for example `n8_u8_m32_a4`), and each
configuration generates one directory; run results are appended to `<work-dir>/results.tsv`, so an
interrupted run can be resumed.

## Generator architecture

The generator has a single one-way data flow:

1. `gen/mmul_gen/instructions/`: one module per instruction. Each module declares one class whose
   attributes are the instruction's name, summary, operands and checking style, plus an ordered
   `templates` tuple listing the scenarios it runs.
2. `gen/mmul_gen/templates/`: one module per template, each a documented `Template` subclass that
   renders one scenario and computes the expected values embedded in it. `gen/mmul_gen/reference.py`
   together with the instruction-independent modules (`numeric_reference`, `fp_semantics`,
   `float_formats`, `generator_types`) is the only shared numerical code.
3. `gen/mmul_gen/catalog.py` is the entire catalog — an explicit, ordered
   `INSTRUCTION_FAMILIES` tuple — plus the generation loop. There is no function-value registry,
   no decorators, no import side effects and no implicit registration step.
4. `gen/mmul_gen/__main__.py` parses the configuration parameters, renders and writes out the source
   files, and can print the catalog (`--list`) or a single family (`--family`).

This separation is deliberate: when reading a new instruction, first look at its instruction class
and its `templates` tuple, then inspect each template's rendering and expected-value computation
one by one. Changing a shared helper should be treated as a cross-family change and accompanied by
targeted unit tests.

`gen/mmul_gen/README.md` documents the architecture, `gen/mmul_gen/instructions/README.md`
documents how instructions declare themselves, and `gen/mmul_gen/templates/README.md` documents the
templates.

### Tests

`python3 -m mmul_gen.tests` runs the generator test suite. `python3 -m tests` (under `gen/`) is the
overall entry point: it runs the shared reference module tests (`numeric_reference`,
`check_manual_sync`, `matrix_geometry`) and dispatches to the generator suite.

`gen/mmul_gen/tests/golden_sources.json` freezes the emitted assembly of five configurations with
SHA-256, so a template change that affects the emitted result fails here.

## Scope and limitations

The generator embeds expected values into every self-checking assembly test. Expected values for
integer 2-D matrix multiply use a NumPy-based reference computation, where the intermediate
quantities are exact Python integers and Ztt wrap-around or saturation is applied explicitly on
write-back. A separate plain Python loop independently computes the same exact matrix result; if
Python and NumPy ever disagree, generation fails before the expected values are embedded into the
assembly. All generated integer 2-D matrix multiply variants use this cross-checked computation to
handle transpose, accumulate/subtract, wrap-around and saturation behavior. The generated matrix
multiply templates also include an explicit mixed signed/unsigned packed-source case with two
different logical input square matrices; its static data layout is visible in the generated assembly
and is checked against the same exact reference. The remaining integer operations and
floating-point expected values use deterministic Python helpers or hand-written values; Ztt
FP8/BF16 encodings, the six rounding modes, exception flags and NaN details are provided by a
dedicated floating-point semantics module (`fp_semantics`).

The elementwise floating-point arithmetic scenarios include quiet NaN propagation, signaling NaN
quieting with `FFLAGS_NV` set, and the invalid-operation pairs `0 * Inf` and `Inf - Inf` on formats
that encode infinity and signaling NaN. E4M3 has no infinity or signaling NaN encoding, so it
produces none of these cases. Other floating-point families such as log/exp/sqrt keep their own
nominal and rounding scenarios.

The generated data, expected offsets and register selection are parameterized over the full
configuration matrix: N (`AME_NELEM`) = 4/8/16/32, UDS=8/16/32, 16 or 32 M registers, and
1/2/4/8/16 accumulators. `run_ztt_tests.py` generates one directory per N/UDS/M/ACC configuration
(120 suites) and runs each source file with a matching runtime JSON configuration. The catalog has
141 ordered definitions, covering 138 architectural instruction mnemonics, and normally emits 141
source files. The three extra definitions/files are two packed-accumulator span checks and one
shared `mmov.a.m`/`mmov.m.a` exception check. A debug move whose element width exceeds one raw row
(`N * UDS` bits, following the manual's row layout) is architecturally illegal and is skipped; for
example at N=4/UDS=8 the pair `mmove64.m.x` and `mmove64.x.m` is omitted, leaving 139 files.

`gen/mmul_gen/instructions/` has one module per instruction and `gen/mmul_gen/templates/` has one
module per template; see `gen/mmul_gen/README.md` for the architecture. The datatype domains and the
individual input recipes are generator choices recorded in the family modules, read directly from
the generated assembly. Instructions with packed, raw transfer, typed broadcast, strided or
conversion-specific rules keep those constraints in the corresponding family templates.

The 2-D floating-point multiply variants accumulate product by product through the destination
dtype, so their all-ones expected value follows sequential rounding: values up to
`2^(mantissa_bits+1)` are exact, and beyond that the RNE tie pins the running sum at that bound (8
for E5M2, 16 for E4M3). Wider formats stay exact for every supported N.

Packed conversions derive their storage/compute pair from the current UDS:

- UDS=8: 4-bit storage, 8-bit compute
- UDS=16: 8-bit storage, 16-bit compute
- UDS=32: 16-bit storage, 32-bit compute

Conversion pairs cover signed and unsigned integer dtypes. Packed storage capability is tracked
separately, because bit-preserving operations may use SAT or floating-point descriptors that are
not legal `mconv.ew` tuples. Debug moves also run in every suite, and compute their raw M register
position wrap-around from the current register width.

To install the generation dependencies in the Python environment selected by CMake:

```sh
python3 -m pip install -r test/ztt/gen/requirements.txt
```

CMake checks that NumPy is importable before generating the tests. The generator suite is run
manually under `gen/`.

The canonical entry point for the generator tests:

```sh
cd sail-ame/test/ztt/gen
python3 -m tests
```

The individual test modules are documented in `gen/tests/README.md`. The scripts under `gen/` are
generator implementations or validation tools, not scattered test entry points.

The generated comments mark the named input case and operand values of each fragment; the
instruction definitions and the generated assembly are themselves the object under inspection.

Sail unit tests additionally cover the encode/disassemble round-trip of the specified instructions
without calling `execute`. They complement the parser, illegal-encoding, fault-atomicity, ordering
and independent reference tests.

Backend ownership helpers are a single-hart bring-up model, and the shared-backend boundary is
explicit. Operating-system software is responsible for saving and restoring AME state using the
architectural instructions `mls.1r`/`mss.1r`, the datatype and status CSRs, and the
`ame.acquire`/`ame.release` protocol. Multi-hart support, wait and timeout progress, backend drain,
cross-hart binding and virtualization ownership are the responsibility of the platform backend
provider, which owns the backend catalog, context-to-backend binding, atomic acquire results, wait
and timeout progress, and drain on release. `extensions.Ztt.ame_backend="shared"` is rejected at
configuration time; `"dedicated"` is the mode supported by this single-hart model.

## Configuration

The Sail configuration layer is the authority that validates the runtime JSON files, including the
Ztt N, UDS, register counts and extension constraints. The assembly generator does not duplicate
these checks: CMake passes the expected N, UDS, M and ACC explicitly via
`--n`/`--uds`/`--m`/`--acc`, and Sail receives the matching JSON at each test run. The generated
suites cover the full N=4/8/16/32 × UDS=8/16/32 × M=16/32 × ACC=1/2/4/8/16 matrix (120
configurations).

To run the generator unit tests:

```sh
cd test/ztt/gen
python3 -m tests
```

## Cross N/UDS configuration smoke test

`src/config/n_config_smoke.S` is compiled once and then run with focused runtime configurations
N=4/16/32 × UDS=8/16/32 generated from `config/config.json.in`. It reads `amenlen` and `ameudsz`,
then executes one integer `madd.ew` with packed UINT8 sources and a UINT16 source/destination. This
lets the test distinguish between the UDS-dependent pack factor and the formed register span (1, 2,
4 for UINT8). A formed UINT16 source and destination always occupy two physical M registers; the
smoke test loads and stores the full span and checks all of its bytes. It also round-trips UINT4
through transposed strided memory and checks every active byte in all `(UDS/4)*N` segments,
including the pack factor 8 case at UDS=32. It complements the full N/UDS/M/ACC generation matrix
and is a single-ELF runtime configuration check.

## Manual synchronization

The manual snapshot is stored in `manual-main/`. From this directory, refresh it from the pinned
prose checkout and regenerate the derived artifacts:

```sh
ruby generators/import_manual_prose.rb
cmake -S ../.. -B ../../build -DCMAKE_BUILD_TYPE=Debug -DENABLE_RISCV_ZTT_TESTS=ON
```

Configuration refreshes the Sail model under `model/extensions/Ztt/` and the `src/ame_macros.inc`
macro include file. The generated assembly test sources are still kept separately under
`build/test/ztt/generated/`.

The test generator's macros and Sail catalog can be checked against the standalone manual snapshot,
so inconsistencies are still detected after a manual update:

```sh
python3 test/ztt/gen/check_manual_sync.py \
  --instruction-data /path/to/sail-ame/test/ztt/manual-main/instructions.json \
  --expected-macros /path/to/sail-ame/test/ztt/src/ame_macros.inc
```

`--strict` fails when the manual instruction set, the macros or the Sail catalog diverge; providing
`--sail-model` also brings the generated Sail instruction catalog into the check. When
`--expected-macros` is provided, the check compares macro encodings byte by byte, including encoding
changes for mnemonics with the same name.

`ZTT_INSTRUCTION_DATA` and `ZTT_EXPECTED_MACROS` can be passed to `build_simulator.sh` to make CMake
perform the strict checks at configuration time. The imported snapshot contains 138 instructions.

To focus the check on one class, for example datatype management:

```sh
python3 test/ztt/gen/check_manual_sync.py \
  --instruction-data /path/to/sail-ame/test/ztt/manual-main/instructions.json \
  --expected-macros /path/to/sail-ame/test/ztt/src/ame_macros.inc \
  --check-instructions agettyp asettyp mgettyp msettyp \
  --strict-selected
```
